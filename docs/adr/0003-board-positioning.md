# ADR-0003: Позиционирование элементов доски (drag-and-drop)

- Status: Accepted
- Date: 2026-06-03
- Authors: @clevergg

## Context

На канбан-доске колонки и карточки имеют порядок, который пользователь меняет
перетаскиванием. Нужно хранить этот порядок в базе так, чтобы перемещение
элемента было эффективным — не требовало переписывать позиции всех соседей.

Затрагивает поля position в моделях Board, Column, Card.

## Decision

Используем дробную позицию (Float). Новая позиция при вставке между двумя
элементами вычисляется как среднее их позиций: (prev + next) / 2.
Перемещение меняет позицию только перемещаемого элемента.

При исчерпании точности Float (когда среднее between соседей совпадает с
соседом) выполняется ребаланс: все элементы контейнера получают заново
позиции с большим шагом (1000, 2000, 3000...), сохраняя текущий порядок.
Логика ребаланса будет реализована в API (фаза работы с карточками).

## Alternatives Considered

### Целочисленная позиция (1, 2, 3)
Отвергнута. Вставка в середину требует сдвига позиций всех последующих
элементов - одно перемещение = массовое обновление строк. Не масштабируется.

### LexoRank (строковые ранги, как в Jira)
Ранг - строка ("a", "an", "aan"...), которую можно удлинять бесконечно,
поэтому теоретически не упирается в предел и не требует ребаланса.
Отвергнута как избыточная для нашего масштаба: сложнее в реализации,
требует библиотеки или нетривиальной логики генерации рангов. Оправдана
на масштабе Jira (миллионы карточек, интенсивное конкурентное редактирование).

### Float (выбрано)
Простой, эффективный (O(1) перемещение - обновляется одна строка),
легко объяснимый. Предел точности Float достигается только после десятков
последовательных вставок в одну точку, что на реальной доске редкость,
и решается ребалансом.

## Consequences

### Положительные
- Перемещение элемента обновляет одну строку, не трогая соседей.
- Простая и понятная реализация (среднее двух соседей).
- Ребаланс как страховка - редкая операция, ~15 строк кода.

### Отрицательные / Trade-offs
- Float имеет конечную точность (~15-17 значащих цифр). При экспоненциальном
  сжатии промежутка (деление пополам) предел достигается за ~50 вставок
  в одну точку. Решается ребалансом контейнера.
- Нужно не забыть реализовать проверку на исчерпание зазора и ребаланс
  в эндпоинте перемещения - иначе в крайнем случае позиции "слипнутся".
