# ADR-0004: RBAC через guards для ролей в workspace

- Status: Accepted
- Date: 2026-06-05
- Authors: @clevergg

## Context

Роли (OWNER/ADMIN/MEMBER/VIEWER) хранятся в модели Member и привязаны к
конкретному workspace. Нужен механизм авторизации: разные эндпоинты требуют
разного уровня прав, причём роль проверяется в контексте workspace из запроса.

## Decision

- Декоратор @Roles(role) помечает минимальную требуемую роль на эндпоинте,
  записывая её в метаданные роута (SetMetadata).
- RolesGuard читает метаданные через Reflector, достаёт workspaceId из URL
  (params), находит запись Member (роль юзера в workspace), сравнивает по
  иерархии.
- Иерархия "роль и выше": числовые веса (OWNER=4, ADMIN=3, MEMBER=2, VIEWER=1),
  проверка вес_юзера >= вес_требуемой. Старшая роль проходит везде, где
  разрешена младшая.
- workspaceId берётся из URL (/workspaces/:workspaceId/...). Guards вешаются
  парой: JwtAuthGuard (аутентификация) затем RolesGuard (роль).
- Отказ прав → 403 Forbidden (отличие от 401 — не аутентифицирован).

## Alternatives Considered

### Источник workspaceId
- Из URL (выбрано): явно, предсказуемо, RESTful. Guard всегда смотрит в params.
- Из тела/гибко: guard усложняется условиями, менее предсказуем. Отвергнуто.
- Вычисление из ресурса (board/card → workspace): нужно для глубоко вложенных
  ресурсов (карточки), добавим позже как расширение guard. Не на старте.

### Иерархия ролей
- Точное совпадение роли: неудобно (OWNER не прошёл бы туда, где нужен ADMIN).
- Иерархия "роль и выше" (выбрано): естественно, старший может всё, что младший.

### Список ролей в @Roles vs одна минимальная
- Список разрешённых ролей: гибче, но избыточно при иерархии.
- Одна минимальная роль (выбрано): благодаря иерархии указание ADMIN
  автоматически включает OWNER. Проще.

## Consequences

### Положительные
- Декларативная защита: @Roles(Role.ADMIN) над эндпоинтом — и всё.
- Переиспользование составного ключа Member (userId, workspaceId) из схемы.
- Иерархия через веса легко расширяется новыми ролями.
- 403 vs 401 — корректная семантика HTTP.

### Отрицательные / Trade-offs
- RolesGuard ходит в базу за Member на каждый защищённый запрос. Для нагрузки
  можно кешировать роли, но на старте приемлемо.
- workspaceId обязан быть в URL — для глубоко вложенных ресурсов (карточки)
  потребуется расширение guard (вычисление workspaceId из ресурса).
